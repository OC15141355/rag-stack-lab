## 1. NVIDIA AI Enterprise lifecycle

- Branches: Feature (FB) ~1 month support, monthly cadence; Production (PB) 9 months from first release, ~6-monthly major, monthly security updates; LTSB 3 years, new one ~every 2.5 years timed to hardware architecture; Infrastructure Branch 1 year (3 years for LTSB Infra), ~6-monthly major, minor every 3 months.
  Source: https://docs.nvidia.com/ai-enterprise/lifecycle/latest/lifecycle-policy.html and .../choosing-a-branch.html
  Implication: PROD should track PB (or LTSB for infra); FB is DEV-only experimentation.
- Layering: Application layer (frameworks, SDKs, NIMs, models) = FB/PB/LTSB. Infrastructure layer (GPU driver, GPU Operator, Network Operator, Run:ai self-hosted) = Infrastructure Branch. Guidance: "Always use an Infrastructure Branch for drivers and operators."
  Source: lifecycle-policy.html. Implication: GPU Operator version is chosen from the Infra branch, not the PB; pin separately.
- NIM Operator is NOT named on the lifecycle, branch or release-notes pages. Its branch/support window is UNVERIFIED (check the Interactive Lifecycle and Compatibility Explorer, or ask the NVIDIA account team). GPU Operator/NIM Operator versions per branch are not listed in release notes either.
- Current branches: PB 6 (first release May 2026, last planned Dec 2026, planned EOL Jan 2027). PB 25h2 EOL July 2026 (one page says Jan 2026 for 25h1; 25h2 dated inconsistently across pages - July 2026 on EOL notices page is the more specific). LTSB 2: first Nov 2024, last planned Aug 2027, EOL Oct 2027. Infra 8.0/8.1 current; Infra 7.x LTSB still supported; Infra 4.x EOL July 2026 ("Do not plan new deployments on Infra 4.x"). PB6 is compatible with Infra 7 or 8.
  Source: https://docs.nvidia.com/ai-enterprise/release-notes/latest/index.html ; https://docs.nvidia.com/ai-enterprise/lifecycle/latest/eol-notices.html
  Implication: PB6 EOL is Jan 2027, i.e. ~5 weeks away; a design adopting PB6 now gets a very short window. Next PB is the target; plan the move. UNVERIFIED: name/date of next PB (not on pages fetched).
- NIM deprecations (EOL notices page): model-specific NIMs Llama-3.1-8B-Instruct, Llama-3.3-70B-Instruct, Llama-3.3-Nemotron-Super-49B-v1.5, Nemotron 3 Nano: "last in PB6; support ends January 2027"; replacement = Model-free NIM for LLMs with model source + profile (Nemotron 3 Nano -> Nemotron 3.5 Lightning or model-free). Llama-3.1-70b-instruct ended July 2026. E5 Embedding v5 deprecated, ends Jan 2027 -> Llama 3.2 1B Embedding v2. TensorRT-LLM backend (*-py3-trtllm) deprecated, last in PB 5.9 -> vLLM backend.   Source: eol-notices.html; release-notes page above.
  Implication: strong vendor steer to the model-free NIM; design NIMService/NIMCache around model-free so model swaps are config, not new NIM image.

## 2a. NIM Operator (partial; sections 2b onward appended below)

- Latest: v3.1.4 (bug fix only: NIMCache auto profile selection when schema v2 manifest lists schema_version after profiles). Release notes carry no dates. Source: https://docs.nvidia.com/nim-operator/latest/release-notes.html
- v3.0.0: Multi-LLM NIM container support for caching and serving, NIM Build CRD, DRA, multi-node via LeaderWorkerSets, KServe. v3.0.2: validation webhooks (default off outside OpenShift; need cert-manager + operator.admissionController.enabled=true); setting both spec.replicas and spec.scale.enabled no longer allowed; multi-LLM NIMService can run without pre-cached models. v3.1.0: Gateway API (spec.expose.router.gateway); spec.expose.ingress DEPRECATED -> spec.expose.router.ingress; DRA now resource.k8s.io/v1 (v1beta2 dropped, breaking for DRA samples). v3.1.1: Model-Free NIM mode (deploy without specifying a model upfront), multi-node via Ray (spec.multiNode.ray). v3.1.2: priorityClassName, large manifests no longer hit ConfigMap limit. v3.1.3: NeMo Microservices CRD management DEPRECATED; NGC API key optional (omit spec.authSecret); scale-to-zero with HPA (feature gate HPAScaleToZero); DRA attributeSelectors[].value now required; OpenShift Helm needs openshift.enabled=true.
- Earlier: v2.0.1 added Hugging Face Hub and NeMo Data Store sources; spec.certConfig deprecated -> spec.proxy. v2.0.0 required spec.image.repository/tag. v1.0.0 "not verified for air-gapped networks" (historic).
- CRD deprecations after 3.1.4: none found (no 3.2 release notes seen). Known: NeMo CRDs deprecated; spec.expose.ingress deprecated.
- Known limitation: NIM LLM 2.0.10 notes say Operator does not support nemotron-3-ultra-550b-a55b (manifest >1 MiB ConfigMap) - search snippet, UNVERIFIED on primary page.
- Implication: pin CRD-affecting fields to non-deprecated forms now (expose.router.ingress, spec.proxy); validate webhooks in DEV/QA with cert-manager.

## 2b. NIM Operator: caching sources, air-gap, upgrade, GPU Operator (retrieved 2026-11-26)

- NIMCache (apiVersion apps.nvidia.com/v1alpha1), exactly one source per cache. Sources: spec.source.ngc (modelPuller = NIM image, authSecret, pullSecret, model.engine/tensorParallelism; or spec.source.ngc.modelEndpoint for Multi-LLM - mutually exclusive with ngc.model); spec.source.hf (endpoint, namespace, modelName or datasetName, authSecret=HF_TOKEN, modelPuller = huggingface-cli image or, for Model-Free NIM, the model-free-nim image e.g. nvcr.io/nim/nvidia/model-free-nim:2.0.2, pullSecret); spec.source.dataStore (NeMo Data Store, HF protocol; endpoint, modelName, namespace, revision). Mirrors (S3/HTTPS/JFrog): env NIM_REPOSITORY_OVERRIDE, or NGC_API_ENDPOINT/NGC_AUTH_ENDPOINT/NGC_API_SCHEME with JFrog URL; no S3 field detail documented.
  Source: https://docs.nvidia.com/nim-operator/latest/cache-llm.html , .../cache.html
- Pre-staged PVC: spec.storage.pvc.create: false + spec.storage.pvc.name (name required if create=false). Warning: create: true means deleting the NIMCache deletes the PVC and cached models. Files must be readable by spec.userID (default 1000)/groupID (2000) on both NIMCache and NIMService; many NFS provisioners ignore fsGroup. Source: https://docs.nvidia.com/nim-operator/latest/air-gap.html . NIMService links via spec.storage.nimCache.name (+ optional profile).
- Custom weights for Multi-LLM / model-free: the cache-llm page documents HF-hub-protocol sources only; local-path/custom-weights field NOT documented there (UNVERIFIED; LoRA via manual PVC copy + NIM_PEFT_SOURCE is LLM-specific only). Practical air-gap route = internal HF-protocol endpoint (hf.endpoint / dataStore.endpoint) or pre-staged PVC.
- Air-gap page lists two options only: proxy to NGC (spec.proxy: httpsProxy/httpProxy/noProxy/certConfigMap) or mirrored local registries. spec.authSecret optional only if all models pre-cached. It does not describe image mirroring or Helm chart mirroring for the operator itself (mirror the chart and operator image yourself). Also NIM LLM air-gap guide: connected phase stages assets, isolated phase mounts them; do not set NGC_API_KEY/HF_TOKEN in isolated phase. https://docs.nvidia.com/nim/large-language-models/3.0.0/deployment/air-gap-deployment.html
- Upgrade: helm repo update; helm show values --version; helm upgrade nim-operator nvidia/k8s-nim-operator -n nim-operator -f values. Helm does not upgrade CRDs: chart ships a pre-upgrade hook (uses operator image; fails if image unpullable) or apply CRDs (nimcaches, nimpipelines, nimservices) manually from the tag first. Operator upgrade does not restart running NIMServices. No version-skew guidance. Source: https://docs.nvidia.com/nim-operator/latest/upgrade.html
  Implication for Argo CD: Helm hooks map to Argo hooks, but CRD update via hook is fragile; prefer a separate Application for CRDs (Replace/ServerSideApply) at an earlier sync wave, with hook disabled (UNVERIFIED value name - check chart values).
- Argo CD / GitOps guidance from NVIDIA for NIM Operator: none found (searched). Ordering NIMCache -> NIMService is documented as "wait for NIMCache Ready"; Argo wave ordering would be my inference (Argo health for custom resources needs a custom health check Lua, not confirmed provided by NVIDIA).
- GPU Operator: latest 26.7.3 (docs 26.7). New GPUCluster CR (26.7.0) cannot coexist with ClusterPolicy; needs Kubernetes >= 1.34.2 for that workflow; containerd min 2.0; DCGM Exporter 4.9.0 renames metrics (breaks dashboards); Helm chart available as OCI artifact in NGC (26.7.0); automatic CRD upgrade via hook (operator.upgradeCRD, since 24.9.0). Air-gap: mirror all images, edit repository/image/version in values; local package mirror ConfigMap for driver or use precompiled driver containers; mirror DRA driver image if GPUCluster. Sources: https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/release-notes.html ; .../26.7/install-gpu-operator-air-gapped.html
  Implication: choose ClusterPolicy vs GPUCluster once; pin precompiled driver containers for air-gap; update Grafana dashboards when bumping.

## 4. Argo CD repo structure and promotion (retrieved 2026-11-26)

Evidence quality: official Argo CD docs for hydrator/best practice; the rest is vendor/community blogs (oneuptime series is single-author, low weight). No CNCF talk was retrieved (UNVERIFIED for talks).

- Config repo separate from app source repo is "highly recommended" (no CI builds on manifest bump, audit, access control, no CI loops). Pin remote bases/charts to tag or SHA, never HEAD. Leave HPA-managed fields (replicas) out of Git. Source: https://argo-cd.readthedocs.io/en/stable/user-guide/best_practices/
- Source Hydrator: BETA (introduced v2.14; docs say beta-quality as of v3.5.0; signature verification v3.5 and commit signing v3.6 alpha). Disabled by default; needs commit-server + hydrator.enabled; write secret; non-root syncSource.path. Limits: drySource and destination must be Git; OCI repos "cannot currently be used as a drySource or hydration destination"; one drySource per Application; stale files not deleted. Argo docs: do not rely on Alpha/Beta in production. Sources: https://argo-cd.readthedocs.io/en/stable/user-guide/source-hydrator/ , .../operator-manual/feature-maturity/ (ApplicationSet progressive syncs also still Beta since v2.6).
  Implication: do not adopt for PROD; incompatible with OCI chart sources, which an air-gapped design will use. Latest Argo CD patch version: UNVERIFIED (docs show 3.5/3.6 era).
- Env-per-branch: called an anti-pattern by Codefresh and Octopus; Octopus recommends folders on one branch; Akuity frames branch/folder/repo as trade-offs (branches unwieldy as stages grow, folders risk drift) and Kargo Render / Argo GitOps Promoter use env branches only as generated output. No Akuity text formally calls it an anti-pattern. Sources: https://codefresh.io/about-gitops/branches-gitops-environments ; https://octopus.com/blog/how-to-model-your-gitops-environments ; https://akuity.io/blog/how-kargo-fixes-gitops-with-promotion ; https://argo-gitops-promoter.readthedocs.io/en/latest/faqs/
  Implication: folder-per-environment (base + per-env overlays/values) on main; promotion = a PR that bumps a pinned version in the next env folder.
- Kargo: Akuity open-source promotion layer (Argo CD deploys, Kargo promotes); Akuity cites 2026 Argo CD User Survey: Kargo use 2% (2025) -> 20% (2026) (vendor-reported). Kargo needs its own controller and can wait for Argo Application Healthy. Air-gap suitability and 1.x maturity: UNVERIFIED (not checked in primary docs). Implication: for 3 clusters and one team, start with PR-based promotion; Kargo is an optional later add.
- Monorepo vs multi-repo: community consensus (blogs only) = monorepo fine for small teams; split on access-control or scale (50+ services). Implication: one config repo for a single team; keep model-weight/image artefacts out of it.
- App-of-apps vs ApplicationSet: community guidance = hybrid (app-of-apps for bootstrap and ordering; ApplicationSet for repetitive per-cluster generation). Reported: sync waves are not effective across ApplicationSet-generated Applications (GitHub issue; progressive sync Beta is the alternative). Sources: https://github.com/argoproj/argo-cd/discussions/11892 ; https://oneuptime.com/blog/post/2026-02-26-argocd-app-of-apps-pattern-at-scale/view (low weight). UNVERIFIED against current Argo CD 3.x docs.
- Sync waves for operators + CRDs: put CRDs in their own Application with ServerSideApply=true (large CRDs), operator in the next wave, CRs after; Argo reports Subscription/Deployment "success" without operator readiness, so a gating Job/health check is needed; app-of-apps child ordering needs the Application health check enabled in argocd-cm. Replace=true for oversized CRDs not confirmed. Source: https://www.redhat.com/en/blog/operator-installation-with-argo-cd/gitops ; oneuptime CRD ordering posts (low weight).
- Helm OCI in Argo CD: repoURL is registry path without oci://, targetRevision = chart version; register with `argocd repo add <registry> --type helm --enable-oci` + creds. Pitfall: Argo shows OCI repo "connected" even when auth fails (argoproj/argo-cd issue 12436) - test with helm registry login/pull. Air-gap pattern: mirror charts+images on connected host, transfer, push to internal registry (Harbor). Sources: https://github.com/argoproj/argo-cd/issues/12436 ; https://goharbor.io/docs/edge/working-with-projects/working-with-oci/working-with-helm-oci-charts/ . NVIDIA publishes GPU Operator chart as OCI on NGC (26.7.0); NIM Operator chart on NGC helm repo (OCI availability UNVERIFIED).

## 5. Bifrost gateway (retrieved 2026-11-26)

- Two modes: (a) config_store.enabled=false: file-only, config.json is sole source, no config UI/API edits, recommended by docs for multinode OSS; (b) DB-backed (SQLite default if config_store omitted, or PostgreSQL) with source_of_truth: "split" (default) or "config.json". Split: file is bootstrap/drift source; unchanged file-backed rows keep UI/API edits; changed rows applied at next startup; removing an entry from the file does NOT delete the DB row. config.json mode: file controls matching DB state; a present-but-empty section can prune DB-only rows; missing section leaves DB alone. Sources: https://docs.getbifrost.ai/deployment-guides/config-json/source-of-truth ; .../config-json/storage
- Applying changes: values are read at startup ("a change rolls the pods" for bifrost.server settings); other changes via helm upgrade. Hot reload semantics for file-only mode not documented (UNVERIFIED). No checksum annotation mentioned (UNVERIFIED in chart templates).
- Helm: official chart `bifrost` (repo alias bifrost/bifrost; chart repo URL not stated on page; source under maximhq/bifrost helm-charts/bifrost, values-examples there). image.tag is required (chart refuses to start without), default repo docker.io/maximhq/bifrost (override for mirror). values map to generated config.json. Secrets: existingSecret options (providerSecrets.<provider>.existingSecret, postgresql.external.existingSecret, encryptionKeySecret); config.json fields accept env.VAR. storage.mode sqlite (StatefulSet+PVC) or postgres (Deployment). Autoscaling off by default. Source: https://docs.getbifrost.ai/deployment-guides/helm/values.md
- No Argo CD/Flux-specific Bifrost guidance found.
- Implication: for GitOps use file-only (config_store disabled) or DB + source_of_truth "config.json"; avoid "split" (UI edits silently diverge from Git, deletions not propagated). Logs/analytics may still need a DB (UNVERIFIED which features require config store).

## Implications for the design

1. Pin PROD to a Production Branch (PB) for NIMs and the Infrastructure Branch (Infra 7.x LTSB or 8.x) for GPU Operator; treat them as two independent version axes in Git. PB6 EOL is Jan 2027 - build the PB-successor bump into the first quarter's plan (next PB name UNVERIFIED).
2. Get NIM Operator's support branch confirmed with the NVIDIA account team; it is not on any public lifecycle page fetched.
3. Prefer Model-Free NIM (NIMCache spec.source.hf + model-free-nim modelPuller, or pre-staged PVC) for LLMs; model-specific NIMs for Llama 3.1-8B/3.3-70B/Nemotron Super 49B/Nemotron 3 Nano end support Jan 2027.
4. Air-gap model flow: internal HF-protocol endpoint or pre-staged PVC (pvc.create: false, name set, matching userID/groupID); no NGC/HF secrets in isolated clusters; mirror NIM images, operator image, chart and GPU Operator images (incl. DRA driver if used) into an internal registry.
5. Argo CD layout: one config repo, folder-per-environment on main, pinned chart versions/image digests, no env branches; promotion by PR (DEV -> QA -> PROD). Kargo optional later; Source Hydrator is Beta and cannot use OCI, so skip it.
6. Bootstrap by app-of-apps with sync waves (CRD App with ServerSideApply -> operators -> NIMCache -> NIMService -> gateway); use ApplicationSets only for per-cluster fan-out of identical apps; verify wave behaviour in DEV (waves across ApplicationSets are reported ineffective).
7. Manage NIM Operator CRD upgrades explicitly (separate CRD Application or manual apply); do not rely on the pre-upgrade Helm hook, which needs the operator image pullable. Add custom health checks for NIMCache/NIMService/ClusterPolicy in argocd-cm (not provided by NVIDIA - UNVERIFIED).
8. Avoid deprecated fields (spec.expose.ingress -> expose.router.ingress, spec.certConfig -> spec.proxy) and NeMo Microservices CRDs; treat NeMo Helix (0.x, Helm, self-managed) as optional and off the critical path.
9. Bifrost: file-only config (config_store disabled) or DB with source_of_truth "config.json", never "split"; secrets via existingSecret/env refs (SOPS or sealed secrets); pin image.tag and mirror docker.io image.
10. Monitor lifecycle: scheduled diff of EOL Notices, EOL Branches, AI Enterprise release notes, NIM LLM and NIM Operator release notes pages (no feed confirmed); GPU Operator bumps need dashboard updates (DCGM metric renames in 26.7.3).
